# 特征删除传播：用户数据移除后如何追到训练集

删除线上数据库的一行，不会自动清除数据湖、特征快照、训练集与模型产物。涉及用户删除、更正或保留期限时，需要把请求变成可追踪的数据工作流；具体法律义务应由组织的法务与隐私团队确认。

## 先画出传播路径

为每类标识建立血缘：原始事件进入哪些分区，派生出哪些特征，哪些训练数据清单引用了这些分区，又产生了哪些模型版本。只记录表名不够，还要记录快照日期、分区和变换版本。

删除请求使用内部稳定主体 ID，避免用可能重复分配的邮箱或手机号。请求本身只保留必要信息，并设置访问控制和审计日志。

## 用墓碑而不是口头通知

将删除意图写成带请求 ID、主体 ID、范围与生效时间的墓碑事件。各下游任务按请求 ID 幂等处理：重复消费不会扩大删除范围，失败后可以安全重试。不可修改的合规归档应按既定策略隔离，不应由普通流水线擅自破坏。

```sql
DELETE FROM training_examples
WHERE subject_id = :subject_id
  AND snapshot_date <= :effective_date;
```

SQL 只是其中一步。派生聚合若无法按主体直接删除，需要从已净化输入重算；向量索引、缓存和离线导出也要列入清单。

## 判断是否需要重训

删除训练样本后，既有权重不一定能逐样本“反向删除”。团队应预先定义阈值与风险规则：是等下一次周期重训、立即从干净检查点重训，还是采用经验证的机器遗忘方法。不要把尚未验证的遗忘算法当成合规保证。

完成证据应包括各存储层处理状态、抽样查询结果、受影响模型清单和后续重训决定。最后从源头到索引做一次反向查询，确认“找不到”不是因为查错了键。
