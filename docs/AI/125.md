# Agent 资源锁：并行步骤修改同一对象时避免互相覆盖

Agent 可以并行读取信息，但两个步骤同时编辑同一工单、文件或部署对象时，后写入者可能静默覆盖前者。资源锁不是为了禁止并行，而是把冲突范围缩到真实共享对象。

## 选择锁粒度

锁键应包含资源类型与稳定 ID，例如 `ticket:8421`，而不是把整个系统锁住。只读操作通常不需要独占锁；写操作在执行前获取带租约的锁，并记录任务 ID、持有者和到期时间。

租约必须有界，防止进程崩溃后永久占用。长操作定期续租，但续租失败就停止写入，不能假定自己仍是持有者。

## 防止过期持有者回写

仅有超时锁还会发生“旧持有者复活”。每次获取锁返回单调递增的 fencing token，下游写入只接受不小于当前 token 的请求。这样旧任务即使恢复，也无法覆盖新任务。

```text
acquire(ticket:8421) -> token 17
acquire after expiry     -> token 18
write with token 17      -> rejected
write with token 18      -> accepted
```

## 冲突时怎么做

获取失败时不要无限重试。根据任务截止时间做有限退避，或将冲突升级为串行计划。锁内只放必要的重新读取、验证和写入；网络搜索等慢操作放在锁外，缩短占用时间。

测试同时启动两个修改相同资源的步骤，确认只有一个提交，另一个能读取新状态后重新规划。再模拟锁持有者暂停到租约过期，验证 fencing token 能拒绝迟到写入。
