# 模型服务就绪探针：区分进程存活与真正可用

容器进程还活着，不代表模型已经能接请求。大模型服务启动时通常要加载权重、分配显存、预热算子；若只用“端口能连接”作为健康检查，流量可能过早进入，第一批请求随即超时。

## 拆成三种信号

- **存活（liveness）**：进程是否卡死；失败后由编排系统重启。
- **就绪（readiness）**：当前实例是否愿意接收新流量；失败时只摘流，不必重启。
- **启动（startup）**：为长时间加载模型提供宽限，避免尚未启动完成就被反复杀死。

就绪条件应至少覆盖：模型文件加载完成、推理引擎已初始化、剩余显存高于安全线，以及一次小型本地推理成功。不要在每次探测时跑完整生成；固定一个极短输入和一个 Token 输出即可，并设置严格超时。

```python
from dataclasses import dataclass

@dataclass
class RuntimeState:
    loaded: bool
    accepting: bool
    free_memory_mb: int
    last_probe_ok: bool

def is_ready(state: RuntimeState) -> bool:
    return (
        state.loaded
        and state.accepting
        and state.free_memory_mb >= 512
        and state.last_probe_ok
    )
```

## 避免探针反噬

探针不能与真实请求争抢昂贵资源。可将轻量自检结果缓存数秒，由后台任务刷新；连续多次失败后再摘流，连续多次成功后再恢复，避免阈值附近抖动。过载时应先把 `accepting` 置为假，让存量请求完成，而不是立即触发重启。

发布验收时记录“进程启动—模型加载—首次就绪”的三个时间点，并在权重、GPU 型号或运行时升级后重新建立基线。好的就绪探针回答的是“现在把一个真实请求交给我是否安全”，而不只是“HTTP 200 能否返回”。
