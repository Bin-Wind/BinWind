# 推理请求优先级：让交互流量不被批任务淹没

在线问答重视尾延迟，离线摘要重视总吞吐。若两类请求进入同一个先进先出队列，一个超长批任务就可能让几十个交互请求排队；简单增加副本只会推迟问题再次出现。

## 先定义服务等级

为请求划分少量、清晰的等级，例如交互、标准和批处理，并为每级写出排队上限、最大输入长度、并发配额与超时。优先级来自可信业务身份，而不能由客户端任意填写，否则所有请求最终都会宣称最高优先级。

调度器可以采用“保留容量 + 加权轮询”：为交互请求预留一部分并发槽，同时允许空闲容量被批处理借用；各队列按权重轮询，避免低优先级永远饿死。已经开始的 GPU 批次通常很难安全抢占，因此要在组批前做选择，并限制单个批次的最大 Token 预算。

```text
交互队列：权重 8，排队上限 2 秒，最大 4k 输入 Token
标准队列：权重 3，排队上限 15 秒，最大 16k 输入 Token
批处理队列：权重 1，可延后，按作业配额限制总 Token
```

## 用正确指标验证

分别观察各等级的排队时间、首 Token 延迟、生成速度、拒绝率和实际 Token 数，不能只看全局平均值。压测要同时注入短交互与长批任务，确认交互 P95 在目标内、批任务仍能持续前进。

过载时优先拒绝尚未进入执行的低等级请求，并返回明确的可重试信息；不要让所有请求一起超时。优先级设计的目的不是让某类工作“永远先走”，而是把有限算力按照公开规则分配，并让降级行为可以预测。
