# 微调断点随机状态：恢复后保持数据顺序可解释

断点续训若只恢复模型与优化器，数据打乱顺序、Dropout 掩码和采样器位置可能全部改变。训练仍能继续，却不再是原运行的延续；损失曲线突然抖动时也很难判断是数据变化还是模型变化。

## 需要一起保存的状态

完整检查点通常包括模型权重、优化器、学习率调度器、梯度缩放器、全局步数，以及 Python、NumPy、训练框架和各设备的随机数生成器状态。分布式采样器还需要当前 epoch、分片规则和已消费位置；流式数据集则要保存游标或可重建的偏移。

保存顺序也很重要：先让所有 Worker 到达一致的安全点，再原子写入临时目录，校验完整后发布检查点清单。不能出现权重属于第 5000 步、采样器却记录第 4999 步的混合状态。

## 做一次确定性验收

在小规模固定环境中训练 N 步并保存，随后：

1. 原进程再运行 5 步，记录样本 ID、学习率和损失；
2. 从检查点启动新进程，也运行 5 步；
3. 比较两边消费的样本顺序与关键状态；
4. 若算子本身非确定，允许数值有已声明容差，但数据序列必须一致。

GPU 数量、框架版本或批大小变化时，完全逐位复现可能不现实。此时不要假装是无缝续训，应将其标记为“分叉恢复”，记录新拓扑和数据边界。可解释的恢复不要求世界永远确定，而是要求团队知道哪些状态被延续、哪些条件已经改变。
