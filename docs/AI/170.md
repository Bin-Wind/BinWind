# RAG 检索追踪 ID：串起改写、召回、重排与引用

用户看到一句错误答案时，团队常只能拿到最终文本，却不知道查询被怎样改写、哪些切片进入候选、重排为何淘汰关键证据。为每次问答建立追踪 ID，可以把分散阶段串成一条可复盘链路。

## 每个阶段记录最小证据

入口生成不可猜测的追踪 ID，并传递给查询改写、关键词检索、向量检索、权限过滤、重排、上下文组装和生成阶段。各阶段记录开始结束时间、配置版本、输入输出对象的稳定 ID与数量。敏感原文可保存脱敏摘要或受控引用，日志中不要复制整份文档。

```json
{
  "trace_id": "01K5...",
  "stage": "rerank",
  "query_version": "rewrite-v7",
  "candidate_ids": ["chunk-a", "chunk-b"],
  "selected_ids": ["chunk-b"],
  "latency_ms": 42,
  "index_snapshot": "kb-2026-09-22"
}
```

引用也应携带切片 ID、文档版本和页码。最终答案只展示适合用户的信息，内部系统则能通过追踪 ID定位到完整阶段。日志设置保留期限和访问控制，并对用户标识做最小化处理。

## 用追踪做评测而非只做排障

抽样追踪可计算召回阶段是否已包含金标准证据、重排是否误删、生成是否使用了已提供证据。延迟也能分解到各阶段，避免把所有慢请求归咎于模型。追踪 ID 本身不会提升质量，但它把“感觉检索有问题”变成可以定位和回归验证的具体失败点。
