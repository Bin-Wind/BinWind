# 用 DVC 管理机器学习数据版本

模型代码能被 Git 追踪，训练数据却常常因为体积大、更新频繁而散落在共享目录里。DVC 的核心思路是：Git 只保存一个很小的描述文件，真实数据进入独立存储。

## 初始化与追踪数据

```bash
python -m pip install dvc
git init
dvc init
mkdir -p data/raw
printf 'text,label\nhello,1\n' > data/raw/train.csv
dvc add data/raw/train.csv
git add .dvc .gitignore data/raw/train.csv.dvc
git commit -m "track training dataset"
```

`train.csv.dvc` 记录文件哈希和大小。数据变化后重新执行 `dvc add`，提交新的描述文件，便能把代码提交与数据快照一一对应。

## 配置远端存储

团队可以使用对象存储、SSH 或共享文件夹。下面用本地目录演示完整流程：

```bash
mkdir -p ../dvc-storage
dvc remote add -d archive ../dvc-storage
dvc push

# 在另一份检出中恢复数据
dvc pull
```

生产项目不要把访问密钥写进仓库。将凭据交给环境变量、云平台身份或 `dvc remote modify --local` 管理。

## 可复现约定

每次实验至少记录代码提交、数据描述文件提交、依赖锁文件、随机种子和训练参数。发布模型时给对应提交打标签，并在模型元数据中保存 Git SHA。这样出现线上回归时，才能准确还原“哪份代码用哪份数据训练出了哪个模型”。

## 常见误区

- DVC 不是数据库，不适合频繁随机更新单条记录。
- 不要直接修改远端存储中的对象，应通过 `dvc push` 写入。
- 大目录要按稳定边界拆分，避免一张图片变化导致整个归档重新上传。
- 删除数据前先确认历史提交仍可从远端恢复，并定期做恢复演练。

数据版本管理的价值不是“多一个工具”，而是让实验结果有证据链。
