# LoRA 适配器合并、切换与版本管理

同一个基础模型可以挂载多个 LoRA 适配器服务不同任务。工程难点往往不是训练，而是确保适配器、基础模型和推理参数之间保持兼容。

## 建立适配器清单

每个适配器至少记录：基础模型精确版本、目标模块、秩 `r`、缩放系数、训练数据版本、模板版本和评估结果。目录可采用：

```text
adapters/
  support-zh-v3/
    adapter_config.json
    adapter_model.safetensors
    manifest.json
```

`manifest.json` 属于团队约定，不要只依赖框架自动生成的配置。

## 运行时切换还是离线合并

运行时加载便于一个基础模型复用多个任务，代价是服务逻辑更复杂；离线合并产物更易部署，但每个任务都要保存完整权重。低频多租户通常适合动态适配器，固定高吞吐服务通常适合预先合并。

使用 PEFT 合并的典型代码如下：

```python
from transformers import AutoModelForCausalLM
from peft import PeftModel

base = AutoModelForCausalLM.from_pretrained("./base-model")
model = PeftModel.from_pretrained(base, "./adapters/support-zh-v3")
merged = model.merge_and_unload()
merged.save_pretrained("./release/support-zh-v3", safe_serialization=True)
```

以上示例需要 `transformers` 与 `peft`，并假设模型已合法下载到本地。

## 合并后的验证

不要认为合并是无损复制。至少对合并前后运行同一批固定输入，比较首 token、生成文本、任务指标、峰值显存和延迟。量化模型上直接合并可能产生额外误差，稳妥做法是在足够精度下合并，再按目标格式量化。

发布时把“基础模型 + 适配器 + 合并脚本”作为可追溯来源，同时对完整产物计算校验和。这样既能快速加载，也保留重新生成的能力。
