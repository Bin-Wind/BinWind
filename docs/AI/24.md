# 微调检查点选择：不要只挑最低 Loss

训练过程中保存多个检查点，最终版本不能只看验证损失。生成任务的 loss 与真实可用性并非完全一致，还要结合任务指标、行为评测和部署成本。

## 建立选择表

对每个检查点记录以下维度：

| 维度 | 示例 | 方向 |
| --- | --- | --- |
| 验证损失 | token-level loss | 越低越好 |
| 任务质量 | 准确率、ROUGE、自定义评分 | 按任务定义 |
| 安全性 | 越权、隐私、危险输出通过率 | 越高越好 |
| 稳定性 | 多随机种子方差 | 越低越好 |
| 运行成本 | 显存、P95 延迟 | 越低越好 |

不要把量纲不同的指标直接相加。先定义硬门槛，淘汰安全或延迟不合格的候选，再在剩余检查点中比较主要质量指标。

## 简单的候选筛选

```python
checkpoints = [
    {"name": "step-500", "quality": 0.82, "safe": 0.99, "p95_ms": 420},
    {"name": "step-1000", "quality": 0.85, "safe": 0.96, "p95_ms": 430},
    {"name": "step-1500", "quality": 0.84, "safe": 0.99, "p95_ms": 425},
]

eligible = [c for c in checkpoints if c["safe"] >= 0.98 and c["p95_ms"] <= 450]
best = max(eligible, key=lambda c: c["quality"])
print(best["name"])
```

这段代码会选择 `step-1500`，体现“门槛优先于单一最高分”。

## 避免评测污染

固定测试集不能反复参与调参，否则它会逐渐变成训练信号。日常迭代用验证集，版本冻结后才运行保留测试集；发现失败样本后，可把同类新样本加入下一轮验证集，但不要悄悄改旧分数。

最终发布报告应包含候选对比、淘汰原因、评测代码版本和人工审阅结论，让检查点选择成为可复核决策。
