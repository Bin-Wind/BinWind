# 推理服务压测：测出容量边界而不是一个 QPS

平均 QPS 无法描述推理系统。提示词长度、输出长度、并发模式和缓存命中都会改变首 Token 延迟、生成速度与显存占用。先从真实流量中提取脱敏分布，再构造短、中、长三组请求。

## 分阶段增加负载

先做单请求基线，再阶梯增加并发，最后加入短时突发。每一档持续到队列和延迟稳定，记录吞吐、TTFT、每 Token 延迟、P50/P95/P99、错误率、队列长度和加速器利用率。到达错误率或尾延迟上限就停止，避免把服务压垮。

容量结论应包含模型版本、量化方式、批处理参数、硬件、输入输出分布和测试时长。例如“在 90% 短请求下可达 40 QPS”不能外推到长文本流量。

用低于拐点的负载设置日常容量，并预留故障转移余量。上线后以相同口径校验真实流量；压测没有覆盖依赖限流、网络抖动和冷启动时，要单独做故障注入。
