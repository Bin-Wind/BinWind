# 设计令牌治理：从命名到发布

设计令牌把颜色、间距、字体等决策变成跨设计与代码共享的数据。真正困难的是命名、语义和变更流程，而不是把色值放进 JSON。

## 三层模型

1. **基础令牌**：`blue-600`、`space-4` 等原始尺度。
2. **语义令牌**：`color-text-primary`、`color-surface-danger`，表达用途。
3. **组件令牌**：`button-primary-background`，只在组件确有独立演进需求时建立。

组件优先引用语义令牌，避免暗色主题或品牌换肤时逐个修改色值。

```json
{
  "color": {
    "blue": { "600": { "$value": "#2563EB", "$type": "color" } },
    "action": { "primary": { "$value": "{color.blue.600}", "$type": "color" } }
  }
}
```

实际格式应与团队使用的转换工具保持一致，并通过 schema 校验别名是否存在、是否形成循环。

## 命名原则

名称描述角色而非当前外观，例如 `text-muted` 优于 `gray-text`。不要把页面名、临时活动名或具体像素值塞进语义层。相同名称必须跨平台表达同一意图，即使 iOS、Web 的最终数值不同。

## 变更流程

每次变更附带视觉对比、受影响组件和迁移说明。删除令牌先标记弃用，统计引用并提供替代项，再在主要版本移除。自动生成代码与文档，禁止手工修改生成文件。

治理的目标不是让令牌数量最大，而是让一次设计决策能安全、可追踪地传播到所有产品表面。
