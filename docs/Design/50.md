# 乐观更新设计：先给反馈，也要为失败准备回路

点赞、重排等高成功率操作可以先更新界面，再在后台提交，让产品显得敏捷。但涉及付款、权限或不可逆动作时，不应仅靠乐观反馈制造“已经成功”的错觉。

## 明确三种状态

用户操作后立即显示预期结果，同时保留“正在同步”的轻量状态。服务端确认后转为稳定状态；失败时恢复原值，并在操作附近说明发生了什么、是否能重试。不要只弹一个几秒后消失的全局 toast。

回滚要保留用户意图。例如编辑标题失败时，把文本放回输入框，而不是恢复旧值后让新内容消失。批量操作发生部分失败时，成功项保持成功，失败项可筛选并重试。

## 处理连续操作

用户可能在第一个请求完成前再次点击。界面应通过请求序号或版本判断迟到响应，不能让旧响应覆盖新状态。对计数器可合并增量，对有顺序的重排则需要明确串行或冲突策略。

## 什么时候不用乐观更新

成功率低、结果依赖复杂校验、后果难以回退或用户必须拿到正式凭证时，先展示处理中，再以服务端结果为准。无论采用哪种模式，都用断网、超时、重复点击和跨设备冲突做原型测试。乐观设计的质量，不只看成功路径有多快，更看失败后用户能否继续。
